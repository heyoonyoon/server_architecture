# 시연 가이드: 2026-08-11 수강신청 장애 재현

이 프로젝트는 2026년 8월 11일 명지대 수강신청 장애를 다시 겪지 않도록 만든 시스템입니다.
이 폴더에는 그날을 그대로 다시 만들어 보는 부하 테스트와, 정원 경쟁을 눈으로 보여 주는 작은 동시성 데모가 들어 있습니다.

그날의 규모는 이렇게 잡았습니다.

- 학생 3,660명 (인문대학 1,748명, 사회과학대학 1,347명, 인공지능소프트웨어융합대학 565명, 2026.04.01 재학생 기준)
- 모두 이미 로그인된 상태에서 10:00 정각에 1~3초 안에 한꺼번에 수강신청 화면으로 들어옴 (그날 장애는 로그인이 아니라 수강신청 진입에서 났습니다)
- 한 사람이 6과목 정도 신청, 전체 약 22,000건 신청 시도
- 인기 분반은 정원보다 몇 배 많은 학생이 몰림

## 준비물

Mac에서 실행합니다. 처음 한 번만 준비하면 됩니다.

- k6: `brew install k6` (부하 발생기, 학생 한 명을 가상 사용자 하나로 흉내 냄)
- node 18 이상 (동시성 데모용, 이미 설치되어 있음)
- `~/.ssh/config`에 sa-db 등 VM 접속 설정 (Mac에서 reset.sh를 돌릴 때 사용)
- 이 폴더를 sa-db의 `~/sa/demo`로 복사: `rsync -a --exclude results demo/ sa-db:~/sa/demo/`

부하 테스트 학생은 학번 30000001 ~ 30003660입니다. 시나리오에서는 로그인 요청을 보내지 않고 `make-tokens.mjs`로 만든 토큰을 씁니다. 직접 로그인해 볼 때 비밀번호는 모두 `loadtest0811`입니다.
학과 id는 `LT-HUM-*`, `LT-SOC-*`, `LT-AI-*`, 과목 id는 `LT001` ~ `LT060`이라 실제 데이터와 섞이지 않습니다.
과목은 6개 시간대 묶음으로 나뉘어 있고, 학생은 묶음마다 한 과목씩 고르기 때문에 시간이 겹쳐서 거절되는 일은 없습니다.
분반 선택은 앞쪽 분반에 몰리도록 치우쳐 있어서(인기 강의), 몇몇 분반은 정원의 몇 배가 몰립니다.

## 시연 순서

### 1. 초기화

sa-db 터미널에서 `demo/reset.sh`

마지막 줄에 `17653-02(id 12) 남은 좌석 5`와 `초기화 완료`가 나오면 깨끗한 상태입니다.
테스트를 돌릴 때마다 먼저 이걸 실행해야 합니다. 이전 테스트 학생들의 입장권(유효 300초)이 남아 있으면 그만큼 입장 자리를 차지해서 다음 테스트가 느려집니다.

### 2. 작은 데모: 정원 5명에 17명이 동시에

Mac에서 `demo/concurrent-enroll.sh`

17명이 로그인하고 대기열을 통과한 뒤, 같은 순간에 17653-02(정원 5) 신청 버튼을 누릅니다.

- 학생별 줄: 응답이 온 순서대로 `성공` 또는 `마감`과 응답 시간
- `성공 5, 정원 마감 12, 오류 0`: Redis Lua 스크립트가 좌석 확인과 차감을 한 번에 처리해서 정원을 넘지 않습니다
- `서버별 분배`: Envoy가 두 gRPC 서버(192.168.64.31, .32)에 번갈아 보낸 건수
- `DB 수강신청 행`, `Redis 남은 좌석`: Kafka를 거쳐 DB에 5건이 쌓이고 Redis 좌석이 0이 되었는지, 셋이 일치하는지

성공한 5명의 응답이 마감된 12명보다 조금 늦게 오는 이유는, 성공한 신청만 Kafka에 이벤트를 쓰고 브로커의 확인(acks=all)을 기다리기 때문입니다.

이 데모가 끝나면 다시 `demo/reset.sh`를 실행합니다.

### 3. 8/11 재현 (실시간 시연, A와 B)

이 단계는 Claude 없이 혼자 진행할 수 있습니다. 같은 3,660명 시나리오를 두 번 돌립니다.

- **A: 대기열 없음** (`QUEUE_MAX_ACTIVE=10000`) 3,660명이 오픈과 동시에 전부 수강신청 화면으로 들어갑니다. 8/11 그날과 같은 상황입니다.
- **B: 대기열 있음** (`QUEUE_MAX_ACTIVE=50`) 대기열이 50명씩만 들여보냅니다.

**수업 전**

1. UTM에서 VM 5대(sa-lb, sa-app1, sa-app2, sa-db, sa-infra)를 켜고 http://192.168.64.30 이 열리는지 확인합니다.
2. (선택) Mac 터미널에서 `node demo/make-tokens.mjs` 로 토큰을 미리 만들어 둡니다. 12시간 유효하고, live.sh도 없으면 알아서 만듭니다.

**수업 중**

1. 화면을 세 개 띄워 둡니다.
   - Grafana: http://192.168.64.34:3000
   - 브라우저: http://192.168.64.30 에서 실제 학생 계정 `20100123` / `20100123`으로 로그인만 해 둡니다
   - Mac 터미널
2. 터미널에서 `demo/live.sh A` (또는 `demo/live.sh B`)

   live.sh가 하는 일은 이렇습니다.
   - sa-infra의 queue-worker 설정을 확인하고, 모드와 다르면 `QUEUE_MAX_ACTIVE`를 바꿔 queue-worker만 다시 띄웁니다(몇 초). 이 값은 queue-worker만 쓰기 때문에 앱 서버는 재시작하지 않습니다. 바뀐 값은 `.env`에 남지 않아서, 나중에 그냥 `docker compose up -d`를 하면 기본값 50으로 돌아갑니다.
   - `reset.sh`로 깨끗한 상태를 만듭니다. 실제 학생 계정(20100123 포함)의 2026-2 신청 기록, 대기열 순번, 입장권도 함께 지워집니다.
   - 토큰이 없거나 25분 안에 만료되면 새로 만듭니다.
   - 30초 카운트다운을 합니다. 마지막 5초는 큰 숫자와 함께 `5초 뒤에 수강신청 진입을 누르세요`가 나옵니다.
3. 화면에 `지금 누르세요!`가 나오는 순간 브라우저에서 **수강신청 진입**을 누릅니다.

   같은 순간 부하 테스트 학생 3,660명이 2초 안에 한꺼번에 대기열에 들어옵니다. B에서는 3,660명 사이의 내 순번이 보이고, 순번이 줄어드는 것을 볼 수 있습니다. 부하 테스트 학생은 3000xxxx 학번만 쓰기 때문에 실제 계정과 겹치지 않습니다.
4. 끝나면 결과 표, 정합성 확인, 서버 부하 최고값, 그리고 다른 모드의 지난 결과와 비교한 줄이 나옵니다. 결과는 `demo/results/runs/<모드>-<시각>/`에 저장됩니다.

결과 표 읽는 법

- `마지막 학생 입장까지`: 오픈부터 3,660번째 학생이 입장권을 받을 때까지 걸린 시간
- `수강신청 시도`, `성공`, `정원 마감`, `오류`: 성공과 정원 마감은 정상 응답이고, 오류는 서버가 처리하지 못한 요청입니다
- `대기열 조회`, `수강신청`의 p95, p99: 요청 100건 중 95번째, 99번째로 느린 응답 시간
- `임계값`: 오류율 1% 미만, 수강신청 p95 1초 미만, 대기열 조회 p95 0.5초 미만을 모두 지켰는지
- `k6 신청 성공`과 `DB 신청 행`이 같으면 Kafka에 들어간 이벤트가 하나도 빠짐없이 DB에 쓰인 것입니다
- `Kafka 반영 완료`: 마지막 성공 응답부터 DB에 모두 쓰일 때까지 걸린 시간
- `정원 초과 강의 0개`, `Redis 좌석 불일치 강의 0개`이면 통과입니다

옵션

- 카운트다운 길이: `COUNTDOWN_S=60 demo/live.sh A`
- 최대 실행 시간: `MAX_DURATION=10m demo/live.sh B` (기본 20분, 넘으면 남은 학생은 멈추고 그때까지 결과를 보여 줍니다)
- 학생 수 줄여서 점검: `STUDENTS=40 COUNTDOWN_S=6 demo/live.sh B`
- k6만 따로: `cd demo && COUNTDOWN_S=30 k6 run loadtest-0811.js`, 정해진 시각에 시작: `START_AT=14:05:00`

**부하 테스트 트래픽이 nginx 대신 Envoy(:8080)로 가는 이유**

sa-lb의 nginx는 CPU 1개라 worker가 1개이고, worker_connections 1024, 파일 디스크립터 한도 1024로 떠 있습니다.
3,660명이 연결을 유지한 채 기다리면 연결 1,000개 근처에서 `accept4() failed (24: No file descriptors available)`가 나면서 연결이 끊깁니다(results/RESULTS.md 2번 참고).
그래서 k6는 같은 VM의 Envoy(http://192.168.64.30:8080)로 바로 보내고, 발표자의 브라우저는 평소처럼 nginx를 거칩니다.
nginx 설정에 `worker_rlimit_nofile 65535;`와 `worker_connections 8192;`를 넣으면 nginx를 거쳐서도 돌릴 수 있습니다. 그때는 `BASE_URL=http://192.168.64.30/api`를 주면 됩니다.

## 대기열 설정과 처리량 (B가 오래 걸리는 이유)

입장권은 학생이 신청을 마쳐도 반납되지 않고, 마지막 요청 후 `PASS_TTL_SECONDS`(300초)가 지나야 풀립니다. 서버 코드에 입장권을 지우는 곳이 만료 정리 말고는 없습니다.
그래서 B가 내보낼 수 있는 학생 수는 대략

```
분당 입장 인원 = QUEUE_MAX_ACTIVE / (신청에 걸리는 시간 + PASS_TTL_SECONDS) x 60
```

이고, 50 / 300초면 분당 약 10명입니다. 3,660명이 모두 입장하려면 약 6시간이 걸리므로, B는 `MAX_DURATION`(기본 20분)에서 멈추고 그때까지의 결과를 보여 줍니다.
측정 결과와 설정별 비교는 `results/RESULTS.md`에 있습니다.
