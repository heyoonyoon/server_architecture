# 시연 가이드: 2026-08-11 수강신청 장애 재현

이 프로젝트는 2026년 8월 11일 명지대 수강신청 장애를 다시 겪지 않도록 만든 시스템입니다.
이 폴더에는 그날을 그대로 다시 만들어 보는 부하 테스트와, 정원 경쟁을 눈으로 보여 주는 작은 동시성 데모가 들어 있습니다.

그날의 규모는 이렇게 잡았습니다.

- 학생 3,660명 (인문대학 1,748명, 사회과학대학 1,347명, 인공지능소프트웨어융합대학 565명, 2026.04.01 재학생 기준)
- 모두 이미 로그인된 상태에서 10:00 정각에 1~3초 안에 한꺼번에 수강신청 화면으로 들어옴 (그날 장애는 로그인이 아니라 수강신청 진입에서 났습니다)
- 한 사람이 6과목 정도 신청, 전체 약 22,000건 신청 시도
- 인기 분반은 정원보다 몇 배 많은 학생이 몰림

## 준비물

Mac에서 실행합니다. 처음 한 번만 준비하면 됩니다.

- k6: `brew install k6` (부하 발생기, 학생 한 명을 가상 사용자 하나로 흉내 냄)
- node 18 이상 (이미 설치되어 있음)
- `~/.ssh/config`에 sa-db, sa-app1 접속 설정 (reset.sh의 DB 작업과 토큰 서명 키 읽기에 사용)
- 이 폴더를 sa-db의 `~/sa/demo`로 복사: `rsync -a --exclude results demo/ sa-db:~/sa/demo/`

학과 id는 `LT-HUM-*`, `LT-SOC-*`, `LT-AI-*`, 과목 id는 `LT001` ~ `LT060`이라 실제 데이터와 섞이지 않습니다.
과목은 6개 시간대 묶음으로 나뉘어 있고, 학생은 묶음마다 한 과목씩 고르기 때문에 시간이 겹쳐서 거절되는 일은 없습니다.
분반 선택은 앞쪽 분반에 몰리도록 치우쳐 있어서(인기 강의), 몇몇 분반은 정원의 몇 배가 몰립니다.

## 시연 순서

### 1. 초기화

Mac 또는 sa-db 터미널에서 `demo/reset.sh`

부하 테스트 학생의 흔적만 지우고, 남은 실제 학생 신청을 기준으로 좌석을 다시 계산합니다. 실제 학생 계정의 신청 기록과 대기열 순번, 입장권은 건드리지 않습니다.
Redis의 오픈 시각(`open:2026-2`)과 동시 입장 한도(`max:2026-2`)도 지웁니다. 한도 키가 없으면 queue-worker는 배포 설정값(`QUEUE_MAX_ACTIVE`, 기본 50)을 씁니다.

### 2. 작은 데모: 정원 5명에 17명이 동시에

이 데모는 실제 학생 계정 17명으로 신청하기 때문에, 17653-02 분반 신청을 먼저 비워야 합니다.

```
demo/reset.sh demo17
demo/concurrent-enroll.sh
```

17명이 로그인하고 대기열을 통과한 뒤, 같은 순간에 17653-02(정원 5) 신청 버튼을 누릅니다. 끝나면 17명의 입장권을 바로 반납합니다.

- 학생별 줄: 응답이 온 순서대로 `성공` 또는 `마감`과 응답 시간
- `성공 5, 정원 마감 12, 오류 0`: Redis Lua 스크립트가 좌석 확인과 차감을 한 번에 처리해서 정원을 넘지 않습니다
- `서버별 분배`: Envoy가 두 gRPC 서버(192.168.64.31, .32)에 번갈아 보낸 건수
- `DB 수강신청 행`, `Redis 남은 좌석`: Kafka를 거쳐 DB에 5건이 쌓이고 Redis 좌석이 0이 되었는지, 셋이 일치하는지

성공한 5명의 응답이 마감된 12명보다 조금 늦게 오는 이유는, 성공한 신청만 Kafka에 이벤트를 쓰고 브로커의 확인(acks=all)을 기다리기 때문입니다.

### 3. 8/11 재현 (실시간 시연, A와 B)

이 단계는 Claude 없이 혼자 진행할 수 있습니다. 같은 3,660명 시나리오를 두 번 돌립니다.

- **A: 대기열 없음** (동시 입장 한도 10000) 3,660명이 오픈과 동시에 전부 수강신청 화면으로 들어갑니다. 8/11 그날과 같은 상황입니다.
- **B: 대기열 있음** (동시 입장 한도 `SLOTS`, 기본 1100) 대기열이 한도만큼만 들여보내고, 신청을 마친 학생이 입장권을 반납하면 다음 학생이 들어갑니다.

가상 학생 한 명은 입장 후 강의 목록을 보고 6과목을 신청한 뒤, 입장 후 7초가 되면 `DELETE /queue`로 입장권을 반납하고 나갑니다. 기다리는 동안에는 서버가 알려 준 간격(2초)으로 대기열을 조회하는데, 이게 "아직 기다리고 있음" 신호입니다. 30초 동안 조회가 없으면 서버가 대기열에서 뺍니다.

**수업 전**

1. UTM에서 VM 5대(sa-lb, sa-app1, sa-app2, sa-db, sa-infra)를 켜고 http://192.168.64.30 이 열리는지 확인합니다.
2. (선택) Mac 터미널에서 `node demo/make-tokens.mjs` 로 토큰을 미리 만들어 둡니다. 12시간 유효하고, live.sh도 없으면 알아서 만듭니다.

**수업 중**

1. 화면을 세 개 띄워 둡니다.
   - Grafana: http://192.168.64.34:3000
   - 브라우저: http://192.168.64.30 에서 실제 학생 계정 `20100123` / `20100123`으로 로그인만 해 둡니다
   - Mac 터미널
2. 터미널에서 `demo/live.sh A` (또는 `demo/live.sh B`)

   live.sh가 하는 일은 이렇습니다.
   - 실제 학생이 대기열에 있거나 입장해 있으면 멈춥니다(발표자 계정 20100123은 예외, 그래도 하려면 `FORCE=1`).
   - `reset.sh`로 부하 테스트 흔적을 지우고, 준비하는 동안 수강신청 진입을 잠급니다(Redis `open:2026-2`를 10분 뒤로).
   - 토큰이 없거나 25분 안에 만료되면 새로 만듭니다(1초).
   - 동시 입장 한도를 Redis `max:2026-2`에 씁니다. queue-worker가 0.5초마다 읽기 때문에 아무것도 재시작하지 않습니다.
   - 전체 예상 시간과, 오픈 0.3초, 0.45초, 0.6초 뒤에 누르면 앞에 몇 명이 있고 몇 초 뒤 입장되는지 미리 보여 줍니다(아래 표의 계산).
   - 가상 학생 3,660명이 모두 뜨면 그 순간부터 5초 뒤를 오픈 시각으로 Redis에 씁니다. 브라우저의 진입 버튼과 가상 학생이 같은 시각에 열립니다.
   - 큰 숫자로 `5초 뒤에 수강신청 진입을 누르세요`, 4, 3, 2, 1, 그리고 `지금 누르세요!`가 나옵니다.
3. 화면에 `지금 누르세요!`가 나오는 순간 브라우저에서 **수강신청 진입**을 누릅니다.

   같은 순간 부하 테스트 학생 3,660명이 2초에 걸쳐 고르게 대기열에 들어옵니다. B에서는 3,660명 사이의 내 순번이 보이고, 순번이 줄어드는 것을 볼 수 있습니다. 부하 테스트 학생은 3000xxxx 학번만 쓰기 때문에 실제 계정과 겹치지 않습니다.
4. 끝나면 결과 표, 정합성 확인, 서버 부하 최고값, 브라우저 사용자가 실제로 기다린 시간(Redis에서 0.2초 간격으로 지켜본 값), 전체 소요 시간, 그리고 다른 모드의 지난 결과와 비교한 줄이 나옵니다. 결과는 `demo/results/runs/<모드>-<시각>/`에 저장됩니다.

결과 표 읽는 법

- `마지막 학생 입장까지`: 오픈부터 3,660번째 학생이 입장권을 받을 때까지 걸린 시간
- `수강신청 시도`, `성공`, `정원 마감`, `오류`: 성공과 정원 마감은 정상 응답이고, 오류는 서버가 처리하지 못한 요청입니다
- `대기열 조회`, `수강신청`의 p95, p99: 요청 100건 중 95번째, 99번째로 느린 응답 시간
- `임계값`: 오류율 1% 미만, 수강신청 p95 1초 미만, 대기열 조회 p95 0.5초 미만을 모두 지켰는지
- `k6 신청 성공`과 `DB 신청 행`이 같으면 Kafka에 들어간 이벤트가 하나도 빠짐없이 DB에 쓰인 것입니다
- `Kafka 반영 완료`: 마지막 성공 응답부터 DB에 모두 쓰일 때까지 걸린 시간
- `정원 초과 강의 0개`, `Redis 좌석 불일치 강의 0개`이면 통과입니다

옵션

- 동시 입장 한도: `SLOTS=500 demo/live.sh B`
- 입장 후 머무는 시간: `SESSION_S=10 demo/live.sh B` (기본 7초)
- 브라우저 사용자 학번: `USER_ID=20100124 demo/live.sh B`
- 최대 실행 시간: `MAX_DURATION=10m demo/live.sh B` (기본 20분)
- 학생 수 줄여서 점검: `STUDENTS=40 demo/live.sh B`

**부하 테스트 트래픽도 nginx를 거칩니다**

k6는 실제 사용자와 똑같이 http://192.168.64.30/api 로 보냅니다.
처음 측정 때 sa-lb의 nginx는 worker 1개, worker_connections 1024, 파일 디스크립터 한도 1024라서 연결 1,000개 근처에서 `accept4() failed (24: No file descriptors available)`가 나며 끊겼습니다(results/RESULTS.md 2번).
그래서 `deploy/lb/nginx/nginx.conf`에 `worker_rlimit_nofile 65535`, `worker_connections 16384`를 넣고, compose에 `ulimits: nofile 65535`, Envoy 쪽 keepalive 연결을 256개로 늘렸습니다.

## 동시 입장 한도 고르기

가상 학생은 오픈 후 2초 동안 고르게(초당 약 1,830명) 들어옵니다. 브라우저에서 오픈 0.45초 뒤에 누르면 앞에 약 820명이 있습니다.
대기열은 0.5초마다 빈자리만큼 입장시키고, 한 자리는 "입장한 학생이 다음 대기열 조회(2초 간격)에서 입장을 알아챔 + 머무는 시간(`SESSION_S`) + 반납"을 거쳐야 다시 빕니다.
그래서 브라우저 사용자의 대기 시간은 두 경우로 갈립니다.

- 앞에 있는 학생 수가 한도보다 적으면: 첫 입장 묶음에 들어가서 바로 입장, 화면에는 첫 조회 때(클릭 2초 뒤) 입장으로 바뀝니다.
- 한도보다 많으면: 첫 묶음의 자리가 비기를 기다려 약 `2 + SESSION_S`초 뒤 입장, 화면에는 그다음 조회 때 바뀝니다.

| SLOTS | SESSION_S | 0.3초 뒤 클릭 | 0.45초 뒤 클릭 | 0.6초 뒤 클릭 | B 전체 |
|---|---|---|---|---|---|
| 1100 (기본) | 7 | 약 2초 | 약 2초 | 약 2초 | 약 32초 |
| 700 | 7 | 약 2초 | 약 10초 | 약 10초 | 약 50초 |
| 500 | 7 | 약 10초 | 약 10초 | 약 10초 | 약 69초 |
| 500 | 3 | 약 6초 (서버 입장 5.3초) | 약 6초 | 약 6초 (서버 입장 5.6초) | 약 40초 |

시간은 클릭부터 화면에 입장이 뜰 때까지이고, 서버가 느려지면 그만큼 늘어납니다. 실행이 끝나면 live.sh가 실제 값(오픈부터 서버 입장 처리까지)을 보여 주고 `run.env`에 `USER_ADMIT_AFTER_OPEN_MS`로 남깁니다.

리허설(`dryrun-active.sh`)에서 지금 VM으로는 동시에 입장해 있는 학생이 150명만 되어도 수강신청 p95가 4.5초, 700명이면 32초까지 늘었습니다(results/RESULTS.md 4번). 한도를 크게 잡으면 B가 빨리 끝나지만 대기열이 서버를 지켜 주는 효과가 줄어듭니다.
