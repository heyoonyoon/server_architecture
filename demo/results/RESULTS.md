## 발견한 것

### 1. 입장권은 시간으로만 풀린다

입장권(Redis `active:2026-2` ZSET)은 마지막 요청 후 `PASS_TTL_SECONDS`가 지나야 빠집니다. 신청을 마치고 나가도 자리를 돌려주지 않고, 서버 코드에 입장권을 지우는 곳(ZREM)이 없습니다.
smoke40에서 확인: 03:34:08에 동시성 데모 학생 17명이 입장, 03:37:38 오픈 때 33명만 들어가고 `active=50`, 나머지 7명은 데모 학생들의 입장권이 만료된 03:39:11(마지막 요청 후 정확히 300초)에 입장했습니다. queue-worker는 0.5초마다 정상 동작했고 상한도 50이 맞았습니다.
`reset.sh`가 `queue:2026-2`, `active:2026-2`를 지우므로 테스트마다 먼저 실행하면 됩니다.

처리량은 대략 `QUEUE_MAX_ACTIVE / (신청 시간 + PASS_TTL_SECONDS)`입니다. 기본값 50 / 300초, 학생 한 명이 신청에 약 7초를 쓰면 307초마다 50명, 분당 약 10명이므로 3,660명이 모두 입장하는 데 약 6시간 10분이 걸립니다.

### 2. 동시 접속의 첫 병목은 nginx 연결 한도

side-login-storm에서 연결을 유지한 학생이 1,000명 근처가 되자 sa-lb nginx가 `accept4() failed (24: No file descriptors available)`를 내며 연결을 끊었습니다.
nginx 컨테이너의 열린 파일 한도가 soft 1024(hard 524288)이고 worker 1개, worker_connections 1024입니다. Envoy는 524288이라 문제가 없습니다.
브라우저도 연결을 유지하므로 지금 설정으로는 동시 접속 약 1,000명이 상한입니다.
해결: nginx.conf에 `worker_rlimit_nofile 65535;`, `events { worker_connections 8192; }`. 그 뒤 실행은 k6만 Envoy(:8080)로 직접 보냅니다.

### 3. 로그인(bcrypt)은 초당 약 18명 (부수 발견)

8/11 장애는 로그인이 아니라 수강신청 진입에서 났기 때문에 재현 시나리오에서는 로그인을 빼고 미리 만든 토큰을 씁니다.
다만 따로 재 보니 bcrypt cost 10 로그인은 두 앱 서버를 합쳐 초당 18.2명(12개 동시 요청 기준)이 한계였고, 3,660명이 모두 로그인하려면 약 200초가 걸립니다.
초당 25명을 밀어 넣은 side-login-storm에서는 로그인 p95가 31.9s까지 늘었습니다(nginx 문제와 겹침).

### 4. 동시에 입장해 있는 학생 수와 서버 한계 (리허설)

`dryrun-active.sh`로 입장권을 미리 준 학생 N명이 동시에 강의 목록을 보고 6과목을 신청하게 했습니다.
정원 초과는 세 번 모두 0건, DB 행 수와 성공 건수도 모두 일치했습니다. 정합성은 부하와 상관없이 지켜졌습니다.
다만 처리량은 gRPC 서버 기준 초당 57 ~ 81건에서 더 오르지 않았고, 동시 입장 150명에서 이미 수강신청 p95가 4.5초, 700명에서는 32초와 오류 2%가 났습니다.

병목 관찰
- 앱 서버: JedisPool 기본 8개, HikariCP 기본 10개 연결로 요청이 연결을 기다리고, 수강신청마다 2026-2 학기 분반 전체(308개)를 DB에서 다시 읽습니다(백엔드 개선 검토 중).
- sa-infra(2 CPU): 리허설 동안 CPU 유휴 2 ~ 8%. 150명 리허설 중 컨테이너별로 enrollment-consumer 73%, Prometheus 18%, Kafka 10%, redis-exporter 10%, Redis 1%.
- sa-db는 이번 리허설에서 CPU를 따로 재지 못했습니다. 다음 측정 때 함께 봐야 합니다.
- 부하 테스트 쪽에서 우회하지 않고 그대로 측정했습니다.

### 5. 리허설 중 실제 사용자 데이터를 지운 문제와 수정

처음 만든 reset.sh는 2026-2 학기 신청 전부와 대기열, 입장권 전체를 지웠습니다. 리허설을 반복하는 동안 실제 학생(예: 60220435)의 대기열 순번과 실제 계정의 신청까지 지워졌고, 동시 입장 한도 50인데 가상 학생 150 ~ 300명에게 입장권을 미리 줘서 실제 사용자가 입장하지 못했습니다.
수정 후 reset.sh는 부하 테스트 학생(30000001 ~ 30003660)의 신청, 대기열, 입장권, 학생별 신청 목록만 지우고, 남은 실제 신청으로 좌석을 다시 계산합니다. 17653-02 분반 동시성 데모를 비울 때만 `reset.sh demo17`을 씁니다.
리허설은 동시 입장 한도를 미리 지급할 인원과 같게 맞춘 뒤 입장권을 주고, 실제 학생이 대기열이나 입장 상태에 있으면 `FORCE=1` 없이는 실행하지 않습니다. live.sh도 같은 검사를 합니다(발표자 계정 제외).
