# 수강신청 서버 아키텍처

## 문제 정의

수강신청은 정해진 시각에 수천 명이 동시에 같은 버튼을 누르는 서비스입니다. 기준으로 삼은 것은 명지대 2026년 8월 11일 수강신청으로, 대상은 인문대학, 사회과학대학, 인공지능소프트웨어융합대학 학생 3,660명이었고 이날 신청 페이지 진입 시점에 장애가 있었습니다.

<img src="docs/images/everytime-0811.png" width="360" alt="8/11 수강신청 당일 에브리타임 글: 앞에 337명 대기 중 안내와 재접속하면 대기시간이 길어진다는 문구, 보자마자 새로고침했다는 댓글">

당일 대기열 안내는 재접속하면 더 기다린다고 했지만, 실제로는 기다린 학생은 계속 접속하지 못하고 새로고침한 학생이 먼저 들어갔습니다. 이 상황에서 풀어야 할 문제는 세 가지입니다.

1. 서버와 DB 과부하: 3,660명이 1~3초 안에 몰리고, 학생 한 명이 약 6과목을 신청해 약 22,000건의 신청이 짧은 시간에 들어옵니다.
2. 정원 초과: 인기 분반 하나에 신청이 몰릴 때 서버 여러 대가 동시에 자리를 차감해도 정원을 넘기면 안 됩니다.
3. 공정성: 기다린 순서대로 들어가야 하고, 새로고침이 이득이 되거나 멈춘 요청에 갇히면 안 됩니다.

## 문제 해결 과정

![수강신청 시스템 인프라 아키텍처](docs/images/architecture.png)

맥 한 대 위 UTM으로 Ubuntu VM 다섯 대(sa-lb, sa-app1, sa-app2, sa-infra, sa-db)를 띄우고 역할별로 Docker 컨테이너를 나눠 올렸습니다. 요청은 그림의 번호 순서대로 흐릅니다.

### 1. 앞단: nginx와 Envoy, 상태 없는 서버 두 대

- nginx가 React 화면을 주고 `/api` 요청을 Envoy로 넘깁니다.
- Envoy가 REST/JSON을 gRPC로 바꾸고(gRPC-JSON transcoder) 서버 두 대에 라운드로빈으로 나눕니다. 요청 제한 시간 5초와 outlier detection을 둬서 응답 없는 서버는 분배 대상에서 빠집니다.
- 서버는 세션을 저장하지 않습니다. 어느 서버가 받아도 같은 결과를 내므로 서버 한 대를 멈춰도 사용자 오류가 없었습니다.

### 2. 인증과 접근 로그: gRPC interceptor

- 로그인하면 서버가 JWT(HS256)를 발급합니다. 두 서버가 같은 비밀키를 쓰므로 app1이 발급한 토큰을 app2가 그대로 검증합니다. 비밀번호는 bcrypt(비용 10)로 저장합니다.
- `AuthInterceptor`가 토큰과 역할(학생, 교수)을 검사해 401, 403을 돌려주고, `AccessLogInterceptor`가 거절과 실패를 포함한 모든 요청을 사용자 ID, 명령, 결과, 시각, 처리 시간과 함께 서버별 텍스트 파일에 한 줄씩 남깁니다. 비밀번호와 토큰은 남기지 않습니다.

### 3. 대기열: Redis와 QueueWorker

- 로그인 뒤 학번을 키로 Redis Sorted Set에 줄을 세웁니다(`ZADD NX`). 새로고침해도 순번이 그대로이고, 한 학생이 여러 번 줄을 설 수 없습니다.
- sa-infra의 QueueWorker 하나가 0.5초마다 "동시 입장 한도 - 현재 입장 인원"만큼만 입장권을 발급합니다. 서버 안에 두면 서버 수만큼 한도가 늘어나므로 따로 뺐습니다.
- 입장권에는 유효 시간이 있고, 신청을 마치면 반납(`DELETE /queue`)합니다. 나간 학생의 자리는 반드시 돌아옵니다.
- 한도 3명, 10명 동시 대기로 확인했을 때 순번이 10, 7, 4, 1, 입장 순으로 줄었습니다.

### 4. 정원 관리: Redis Lua 원자 차감

- 중복 신청 확인, 정원 확인, 자리 차감을 Redis Lua 스크립트 한 번으로 묶었습니다. Redis는 스크립트를 하나씩 실행하므로 서버 두 대가 동시에 요청해도 자리가 두 번 차감되지 않습니다.
- 선수과목, 시간 충돌, 같은 과목 다른 분반, 신청 가능 학점은 차감 전에 검사합니다.

### 5. 저장: Kafka와 Consumer, PostgreSQL

- 신청 결과는 Kafka에 이벤트로 남기고, Kafka가 저장을 확인(`acks=all`)한 뒤에만 성공을 응답합니다. 기록에 실패하면 차감한 자리를 되돌립니다.
- enrollment-consumer가 이벤트를 읽어 PostgreSQL에 저장합니다. 저장이 끝난 뒤에만 offset을 확정하고, 다시 읽은 메시지는 `ON CONFLICT`로 무시합니다. 순간 폭주를 DB가 직접 받지 않게 하고, DB가 잠시 멈춰도 기록을 잃지 않기 위한 구조입니다.

### 6. 업무 규칙 위반: CustomException

- 시간이 겹치는 강의를 신청하면 서버가 `CustomException(ABORTED, 메시지)`을 던지고, 이를 gRPC Status로 바꿔 돌려줍니다. Envoy가 HTTP 오류로 바꾸고, 웹 화면은 서버가 보낸 메시지("신청한 강의(...)와 시간이 겹쳐 수강신청할 수 없습니다.")를 그대로 알림창에 띄웁니다.

### 7. 모니터링: Prometheus와 Grafana

- Prometheus가 Envoy, nginx, PostgreSQL, Redis 지표를 5초마다 모으고 Grafana 대시보드로 봅니다. VM CPU는 각 VM에서 `vmstat 1`로 따로 쟀습니다.

## 의의

- 정합성과 처리량을 나눠서 풀었습니다. 정원은 Redis Lua 한 곳에서만 결정하므로, 응답이 60초씩 밀리던 과부하 상황에서도 정원 초과와 Redis, DB 불일치가 한 번도 나지 않았습니다.
- 8/11 장애의 모습(서버는 살아 있는데 요청이 503이나 시간 초과로 끝남)을 Envoy 서킷 브레이커와 대기열 조회 폭주로 실제로 재현하고, 원인을 수치로 확인했습니다.
- 추측이 아니라 측정으로 병목을 옮겨 가며 고쳤습니다. DB, 커넥션 풀, Envoy 상한, 대기열 조회 순으로 병목이 바뀌는 것을 CPU와 응답 시간으로 확인했습니다.
- 학번 기반 대기열로 새로고침해도 순번이 유지되고, 입장권 유효 시간과 반납으로 자리가 묶여 줄이 멈추는 문제를 막았습니다.

## 한계

- 3,660명 전체 B는 개선 후에도 약 5분 걸리고 신청 오류율 4.00%가 남았습니다. 0 오류를 확인한 것은 1,830명입니다. 같은 1,830명을 나중에 다시 돌린 실행(`B-1015-112537`)에서는 오류 23건(0.21%), 수강신청 p95 8.9초로 결과가 흔들렸습니다.
- k6에 정한 응답 시간 목표(수강신청 p95 1초, 대기열 조회 p95 0.5초 등)는 모든 실행에서 넘지 못했습니다.
- 개설 강의 캐시는 서버마다 60초마다 갱신합니다. 한 서버에서 과목을 추가하거나 지우면 다른 서버는 최대 60초 동안 이전 목록을 볼 수 있습니다.
- 대기열 조회 간격이 5초라 입장 처리 뒤 화면에 입장이 뜨기까지 최대 5초가 더 걸립니다.
- 앱 VM은 2 vCPU, sa-lb와 sa-db는 1 vCPU입니다. 개선 후에도 앱 VM과 sa-lb CPU 최고값이 99~100%에 닿았습니다.
- 앱 서버 JVM 지표와 VM 노드 지표는 Prometheus에 없어 `vmstat`으로 따로 쟀고, Envoy의 서버별(endpoint) 통계도 켜지 않았습니다.
- Redis, Kafka, PostgreSQL이 각각 한 대뿐이라 단일 장애 지점이고, Kafka 복제로 유실을 막는 보장도 없습니다. 서버가 자리를 차감한 직후 Kafka 기록 전에 죽으면 자리만 줄어드는데, 이를 맞추는 Redis, DB 대조 작업은 만들지 않았습니다.
- JWT는 라이브러리 없이 `javax.crypto`로 직접 구현해 검증된 라이브러리만큼 검토되지 않았습니다.
- 로그인(bcrypt)은 두 서버 합쳐 초당 약 18명이 한계라, 재현 시나리오는 미리 로그인한 토큰으로 시작합니다.
- VM 다섯 대와 부하 생성기(k6)가 모두 맥 한 대 위에서 돌아 서로 CPU를 나눠 씁니다. 실제 서비스 규모의 수치로 그대로 옮길 수는 없습니다.
- 학점 한도 초과와 DLT 경로는 시드 데이터로 재현할 조합이 없어 직접 확인하지 못했습니다.
