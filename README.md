# 수강신청 서버 아키텍처

## 문제 정의

수강신청은 정해진 시각에 수천 명이 동시에 같은 버튼을 누르는 서비스입니다. 기준으로 삼은 것은 명지대 2026년 8월 11일 수강신청으로, 대상은 인문대학, 사회과학대학, 인공지능소프트웨어융합대학 학생 3,660명이었고 이날 신청 페이지 진입 시점에 장애가 있었습니다.

<img src="docs/images/everytime-0811.png" width="360" alt="8/11 수강신청 당일 에브리타임 글: 앞에 337명 대기 중 안내와 재접속하면 대기시간이 길어진다는 문구, 보자마자 새로고침했다는 댓글">

당일 대기열 안내는 재접속하면 더 기다린다고 했지만, 실제로는 기다린 학생은 계속 접속하지 못하고 새로고침한 학생이 먼저 들어갔습니다. 이 상황에서 풀어야 할 문제는 세 가지입니다.

1. 서버와 DB 과부하: 3,660명이 1~3초 안에 몰리고, 학생 한 명이 약 6과목을 신청해 약 22,000건의 신청이 짧은 시간에 들어옵니다.
2. 정원 초과: 인기 분반 하나에 신청이 몰릴 때 서버 여러 대가 동시에 자리를 차감해도 정원을 넘기면 안 됩니다.
3. 공정성: 기다린 순서대로 들어가야 하고, 새로고침이 이득이 되거나 멈춘 요청에 갇히면 안 됩니다.

### 출발점

목표는 단순했습니다. 위의 8/11 상황, 즉 3,660명이 같은 순간에 몰려도 서버가 버티고, 정원이 넘치지 않고, 기다린 순서대로 들어가는 아키텍처를 직접 설계해 보는 것이었습니다.

먼저 8/11에 무엇이 터졌는지부터 나눠 생각했습니다. 정각의 진입은 모두가 같은 순간 같은 무거운 일을 하는 요청량 문제이고, 진입 뒤 과목별 신청은 인기 분반 하나의 정원에 동시 쓰기가 몰리는 경합 문제입니다. 성격이 다르니 따로 풀기로 했습니다.

### 몰리는 사람을 어떻게 받을까

가장 먼저 정한 것은 데이터를 PostgreSQL에 두고, DB, 서버, 로드밸런서를 Docker 컨테이너로 나눠 나중에 각각 다른 VM에 올릴 수 있게 하는 것이었습니다. 그리고 정각의 폭주는 대기열(Waiting Room)로 받기로 했습니다.

대기열 저장소로는 Redis를 골랐습니다. 처음에는 라이브러리를 최소화하려 했지만, 대기열과 캐시는 현업과 같은 구성을 쓰는 쪽을 우선했습니다.

줄을 세우는 키를 정할 때 많은 서비스가 쓰는 익명 번호표와 비교했습니다. 번호표는 새로고침이나 재시작으로 잃으면 맨 뒤로 밀립니다. 그래서 로그인한 뒤 학번을 키로 Redis Sorted Set에 넣고, 이미 있으면 덮어쓰지 않게(`ZADD NX`) 했습니다. 새로고침해도 순번이 유지되고 한 학생이 여러 번 줄을 설 수 없습니다. 대가는 로그인이 대기열의 보호를 받지 못한다는 점입니다. 비밀번호 해시는 일부러 느린 계산이라, 오픈 전에 미리 로그인하게 해서 로그인 부하는 시간에 나누고 정각의 폭주는 가벼운 대기열이 받도록 나눴습니다. 순번 조회도 클라이언트가 마음대로 하지 않고, 서버가 응답에 담아 준 간격으로만 하게 했습니다.

### 8/11은 정확히 어디서 무너졌을까

규모를 정하려고 명지대 학생 현황으로 8/11 대상 인원을 셌습니다. 인문대학 1,748명, 사회과학대학 1,347명, 인공지능소프트웨어융합대학 565명으로 3,660명입니다. 이들이 10시 정각 1~3초 안에 들어오고 한 명이 약 6과목을 신청하면 약 22,000건입니다. 이 상황을 대기열 없음(A)과 대기열 있음(B)으로 재현해 비교하기로 했고, 과제가 요구하는 gRPC 서버와 클라이언트만 직접 만들고 부하 생성(k6), 로드밸런서, 저장소, 모니터링은 기성 도구를 쓰기로 했습니다.

처음에는 응답이 느려지자 학생들이 새로고침을 반복해 부하가 몇 배로 늘었다고 추정했습니다. 그런데 당일을 다시 떠올리니 맞지 않았습니다. 기다린 학생은 계속 접속하지 못했고, 새로고침한 학생은 바로 들어갔습니다. 서버에 여유가 있었는데 기존 요청이 느린 게 아니라 죽어 있었다는 뜻입니다. 그래서 원인을 멈춘 서버가 로드밸런서 목록에 남아 있었거나, 요청에 제한 시간이 없었거나, 대기열 자리가 반납되지 않은 것으로 다시 좁혔습니다.

이 세 가지를 설계에 그대로 반영했습니다. 응답 없는 서버는 로드밸런서가 빼고, 세션 고정 없이 어느 서버로 가도 되게 하고, 모든 호출에 제한 시간을 두고, 입장 자리에는 유효 시간을 둬서 반드시 반납되게 했습니다. 정원 경합은 Redis에서 확인과 차감을 한 번에 하는 원자적 차감과 짧은 DB 트랜잭션으로 풀기로 했습니다. DB 행 잠금으로 처리하면 잠금 대기가 길어질수록 연결을 오래 붙잡아 전체 지연으로 번질 수 있기 때문입니다.

### 입장은 누가, 얼마나 정할까

입장 방식은 동시 입장 한도를 정해 두고 "한도 - 살아 있는 입장권 수"만큼만 들여보내는 방식으로 했습니다. 응답 속도를 보고 한도를 자동으로 조절하는 방식도 있지만, 그런 방식은 주로 서버 자기 보호 계층에서 쓰이고 대기열에 쓰면 입장 속도가 출렁여 대기 시간을 예측하기 어렵습니다. Cloudflare Waiting Room 같은 제품도 운영자가 고정 한도를 정합니다.

입장 처리는 queue-worker 컨테이너 하나가 맡게 했습니다. 서버 여러 대가 각자 세면 한도가 서버 수만큼 늘어나기 때문입니다. Redis 스크립트로 서버들이 나눠 처리하는 방법도 있었지만 단순한 쪽을 택했습니다. 부하 테스트 중 무엇이 병목인지 보려고 Prometheus와 Grafana도 이때 넣기로 했습니다.

### 브라우저에서 gRPC 서버를 어떻게 부를까

기능이 많아져 클라이언트를 콘솔에서 웹(React)으로 바꿨는데, 브라우저는 gRPC를 직접 쓸 수 없습니다. 처음에는 서버 코드를 그대로 둘 수 있는 gRPC-Web과 Envoy를 골랐습니다. nginx에는 gRPC-Web 변환 기능이 기본으로 없고, Envoy는 gRPC-Web 공식 문서가 안내하는 기본 프록시이면서 로드밸런싱, 헬스체크, 타임아웃을 함께 해 주기 때문입니다.

나중에 브라우저에서 gRPC-Web을 쓰는 것은 현업에서 드물다고 보고, 밖은 REST, 안은 gRPC인 일반적인 구조로 바꿨습니다. Envoy의 gRPC-JSON transcoder를 쓰면 proto에 HTTP 경로만 적으면 되므로 Java 서버 코드는 바꾸지 않았습니다.

### DB 저장에 Kafka가 필요할까

쓰기량만 보면 Kafka는 필요 없었습니다. 22,000건을 30~60초에 저장하면 초당 약 400~700건이고, PostgreSQL 한 대로 감당할 수 있는 범위입니다. 그래서 Kafka가 필요해지는 신호를 따로 정리했습니다. 지속적인 쓰기가 DB 한계에 가까울 때, 같은 이벤트를 여러 서비스가 소비해야 할 때, 장애 동안 이벤트를 보관하거나 다시 재생해야 할 때입니다.

결국 "DB를 쉽게 키울 수 없는 상황"을 전제로 Kafka를 넣었습니다. Kafka가 푸는 것은 순간 폭주이고, 들어오는 양이 DB 처리량보다 계속 많으면 밀린 양이 끝없이 쌓인다는 한계도 함께 적어 두었습니다. 넣기 전에 "성공이라고 알렸는데 저장이 실패하면?"부터 정했습니다. Kafka가 저장을 확인(`acks=all`)한 뒤에만 성공을 알리고, 실패하면 Redis 자리를 되돌립니다. consumer는 DB 저장 뒤에만 읽은 위치를 확정하고 중복은 `ON CONFLICT`로 무시하며, 재시도해도 안 되는 메시지는 실패 전용 토픽(DLT)으로 보냅니다.

### 로그인과 로그

스키마는 Flyway로 버전 관리하게 했습니다. 서버 두 대가 같은 순간 시작해도 한 대만 적용되는 것을 확인했습니다.

인증은 로그인 뒤 JWT를 발급하는 방식으로 했습니다. 두 서버가 같은 비밀키를 쓰므로 어느 서버가 받아도 검증할 수 있고 세션을 저장하지 않습니다. 실제로 app2가 발급한 토큰이 app1에서 그대로 통과했습니다. 토큰 검사와 역할별 권한, 과제가 요구한 로그(사용자 ID, 명령, 시각)는 모든 요청에 똑같이 붙어야 해서 gRPC interceptor에 두었습니다. 가장 바깥 interceptor가 거절과 실패까지 포함해 한 줄씩 기록하고 비밀번호와 토큰은 남기지 않습니다.

비밀번호 해시는 처음에 PBKDF2(60만 회)를 직접 조립했고 VM 로그인 평균이 236ms였습니다. 사전 로그인이 필요하다는 근거를 이 수치로 확인했습니다. 이후 bcrypt 라이브러리로 바꿨는데, 비용 12에서는 평균 724ms로 너무 느려 OWASP 최솟값인 비용 10으로 낮췄습니다.

### 수강신청을 붙이고 동시성을 확인하기

수강신청은 같은 서버에 EnrollmentService로 붙이고, queue-worker와 enrollment-consumer는 실행 시작점만 다른 프로세스로 sa-infra에 두었습니다. 신청 성공 여부는 Redis Lua 한 번(중복, 정원, 차감)으로 바로 정하고, Kafka에 기록한 뒤 응답합니다. 선수과목, 시간 충돌, 같은 과목 다른 분반, 학점 한도는 그 앞에서 검사합니다.

가장 확인하고 싶었던 것은 정원이었습니다. 정원 5명인 분반에 학생 17명이 동시에 출발하도록 맞춰 신청하게 했더니, 서버 두 대가 8건, 9건씩 나눠 받았는데 성공 5, 정원 마감 12, 오류 0, 전체 367ms였고 Redis 남은 자리 0, DB 기록 정확히 5건이었습니다. 대기열은 한도 3명으로 줄여 10명을 세웠을 때 순번이 10, 7, 4, 1, 입장 순으로 줄었습니다.

### 실제 인원으로 부하를 걸어 보니

40명 점검에서 첫 문제가 나왔습니다. 입장권이 마지막 요청 후 300초가 지나야만 풀려서, 신청을 마치고 나가도 자리가 돌아오지 않았습니다. 이대로면 3,660명이 다 들어가는 데 약 6시간이 걸립니다. 그래서 신청을 마치면 입장권을 반납하는 기능과, 응답 없는 대기자를 줄에서 빼는 기능을 넣었습니다.

3,660명 로그인을 시험하자 sa-lb의 nginx가 연결 약 1,000개에서 파일 디스크립터가 바닥나 연결을 끊었습니다. nginx 연결과 파일 한도를 올렸습니다. 로그인(bcrypt)은 두 서버 합쳐 초당 약 18명이 한계였고, 8/11 장애는 로그인이 아니라 진입에서 났으므로 재현은 미리 받은 토큰으로 시작하게 했습니다.

입장권을 미리 준 150, 300, 700명 리허설에서는 정원 초과가 모두 0이었지만 처리량이 초당 57~81건에서 더 오르지 않았습니다. 정합성은 부하와 상관없이 지켜지고, 응답 시간이 무너지는 구조라는 것을 이때 알았습니다.

### 병목을 하나씩 옮겨 가며 고치기

개선 전 빌드로 3,660명 기준선을 쟀습니다. 대기열 없는 A에서는 sa-db(1 vCPU)가 측정 구간 대부분 CPU 90% 이상, 평균 98%였습니다. 수강신청과 강의 목록이 요청마다 학기 분반 308개를 DB에서 다시 읽었고, 앱 서버는 CPU 40% 정도로 여유가 있는데도 DB 연결 10개, Redis 연결 8개를 기다렸습니다. 요청이 쌓이자 Envoy의 동시 요청 기본 상한 1,024에 걸려 약 7,055건이 503으로 거절됐습니다. 8/11에 학생들이 본 접속 오류와 같은 모습이었지만 정원 초과는 0이었습니다. 대기열을 켠 B는 신청 오류율을 16.28%에서 5.01%로 낮췄지만 DB는 여전히 평균 91%였습니다.

그래서 개설 강의 목록을 서버 메모리에 두고 60초마다 갱신하고(`OfferingCatalog`), 남은 좌석은 Redis에서 읽고, 연결 풀을 Redis 128개, DB 30개로 늘렸습니다. 3,660명 B에서 sa-db CPU는 평균 25%, 수강신청 p95는 11.7초에서 2.0초로 내려갔습니다.

DB가 풀리자 병목은 대기열 조회로 옮겨 갔습니다. 3,000명 넘는 대기자가 2초마다 순번을 물어 조회가 60초 제한에 걸렸습니다. 1,830명으로 줄여 보니 이번에는 대기열 조회가 Envoy 상한 1,024에 걸려 HTTP 실패율 15.15%, 중도 포기 239명이 났습니다. 상한을 10,000으로 올리자 0.00%, 0명이 됐고, 남은 조회 p99 36.5초는 조회 간격을 2초에서 5초로 늘려 5.9초로 줄였습니다. 입장을 알아채는 데 최대 5초가 더 걸리는 것은 받아들였습니다.

### 규칙 위반을 사용자에게 정확히 알리기

마지막으로 시간이 겹치는 강의를 신청했을 때 서버가 `CustomException`을 던지고, 이를 gRPC Status로 바꿔 "신청한 강의(...)와 시간이 겹쳐 수강신청할 수 없습니다."를 그대로 돌려주게 했습니다. 웹 화면은 이 메시지를 알림창에 띄웁니다. 상태 코드는 `ABORTED`로 했습니다. 이 서버에서 `FAILED_PRECONDITION`은 입장권 만료와 오픈 전 진입에 쓰고 웹은 이 코드를 받으면 대기열로 돌려보내므로, 같은 코드를 쓰면 규칙 위반 하나로 학생이 줄 밖으로 밀려나기 때문입니다.

## 의의

- 정합성과 처리량을 나눠서 풀었습니다. 정원은 Redis Lua 한 곳에서만 결정하므로, 응답이 60초씩 밀리던 과부하 상황에서도 정원 초과와 Redis, DB 불일치가 한 번도 나지 않았습니다.
- 8/11 장애의 모습(서버는 살아 있는데 요청이 503이나 시간 초과로 끝남)을 Envoy 서킷 브레이커와 대기열 조회 폭주로 실제로 재현하고, 원인을 수치로 확인했습니다.
- 추측이 아니라 측정으로 병목을 옮겨 가며 고쳤습니다. DB, 커넥션 풀, Envoy 상한, 대기열 조회 순으로 병목이 바뀌는 것을 CPU와 응답 시간으로 확인했습니다.
- 학번 기반 대기열로 새로고침해도 순번이 유지되고, 입장권 유효 시간과 반납으로 자리가 묶여 줄이 멈추는 문제를 막았습니다.

## 한계

- 3,660명 전체 B는 개선 후에도 약 5분 걸리고 신청 오류율 4.00%가 남았습니다. 0 오류를 확인한 것은 1,830명입니다. 같은 1,830명을 나중에 다시 돌린 실행(`B-1015-112537`)에서는 오류 23건(0.21%), 수강신청 p95 8.9초로 결과가 흔들렸습니다.
- k6에 정한 응답 시간 목표(수강신청 p95 1초, 대기열 조회 p95 0.5초 등)는 모든 실행에서 넘지 못했습니다.
- 개설 강의 캐시는 서버마다 60초마다 갱신합니다. 한 서버에서 과목을 추가하거나 지우면 다른 서버는 최대 60초 동안 이전 목록을 볼 수 있습니다.
- 대기열 조회 간격이 5초라 입장 처리 뒤 화면에 입장이 뜨기까지 최대 5초가 더 걸립니다.
- 앱 VM은 2 vCPU, sa-lb와 sa-db는 1 vCPU입니다. 개선 후에도 앱 VM과 sa-lb CPU 최고값이 99~100%에 닿았습니다.
- 앱 서버 JVM 지표와 VM 노드 지표는 Prometheus에 없어 `vmstat`으로 따로 쟀고, Envoy의 서버별(endpoint) 통계도 켜지 않았습니다.
- Redis, Kafka, PostgreSQL이 각각 한 대뿐이라 단일 장애 지점이고, Kafka 복제로 유실을 막는 보장도 없습니다. 서버가 자리를 차감한 직후 Kafka 기록 전에 죽으면 자리만 줄어드는데, 이를 맞추는 Redis, DB 대조 작업은 만들지 않았습니다.
- JWT는 라이브러리 없이 `javax.crypto`로 직접 구현해 검증된 라이브러리만큼 검토되지 않았습니다.
- 로그인(bcrypt)은 두 서버 합쳐 초당 약 18명이 한계라, 재현 시나리오는 미리 로그인한 토큰으로 시작합니다.
- VM 다섯 대와 부하 생성기(k6)가 모두 맥 한 대 위에서 돌아 서로 CPU를 나눠 씁니다. 실제 서비스 규모의 수치로 그대로 옮길 수는 없습니다.
- 학점 한도 초과와 DLT 경로는 시드 데이터로 재현할 조합이 없어 직접 확인하지 못했습니다.
