# 최소 자원 탐색 실험 계획

## 1. 목적

명지대 수강신청 오픈처럼 학생 3,660명이 한꺼번에 들어올 때 시스템이 실패하지 않는 최소 자원을 찾습니다.
부하는 고정하고 자원만 넉넉한 구성에서 작은 구성으로 줄여 가며, 통과 기준이 처음 깨지는 지점의 직전 구성을 최소 구성으로 정합니다.

## 2. 고정 부하

| 항목 | 값 |
|---|---|
| 학생 | 30000001 ~ 30003660, 3,660명, 비밀번호 loadtest0811, 수강 이력 없음, 최대 18학점 |
| 도착 | 오픈 시각부터 2초 안에 모두 도착 (`ARRIVAL_SPREAD_S=2`) |
| 학생 한 명의 흐름 | Login, EnterQueue, WatchQueue 서버 스트림으로 입장 대기, ListOfferings, Enroll 1 ~ 2과목, ListMyEnrollments, LeaveQueue |
| 신청 대상 | 개설 강의 101 ~ 110 (과목 90001 ~ 90005, 과목마다 2개 분반, 분반 정원 300명, 합계 3,000석) |
| 분반 선택 | 서로 다른 과목 1 ~ 2개를 고르고 과목 안에서 분반을 무작위로 고름, 앞 번호 과목에 몰리도록 치우침 (`SKEW=1.5`) |
| 부하 발생 | Mac의 k6 v2.3.0, gRPC로 sa-lb Envoy `192.168.64.30:8080` 에 직접 연결 |

신청 시도는 약 5,500건이고 좌석은 3,000석이므로 정원 마감 응답이 반드시 생깁니다. 정원 마감과 같은 과목 중복 같은 업무상 거절은 오류로 세지 않고, UNAVAILABLE 과 DEADLINE_EXCEEDED 처럼 서버가 처리하지 못한 응답만 오류로 셉니다.

## 3. 통과 기준

비교 대상은 이전 구조의 3,660명 실행(`B-1015-045608`)이며, 이때 수강신청 오류율은 4.00%(831건)이고 수강신청 p95 는 1,986ms 였습니다. 아래 조건을 모두 만족해야 통과입니다.

| 기준 | 조건 | 측정 위치 |
|---|---|---|
| 수강신청 오류율 | 4.00% 미만 | k6 `enroll_error_rate` |
| 전체 RPC 오류율 | 4.00% 미만 | k6 `rpc_error_rate` |
| 수강신청 지연 | p95 2,000ms 이하 | k6 `grpc_req_duration{name:enroll}` |
| 정원 초과 | 0건, 분반 101 ~ 110 각각 300명 이하이고 합계 3,000건 이하 | Data `enrollments` |
| 저장 정합성 | Data 의 부하 학생 ENROLLED 행 수가 k6 성공 건수와 같음 | Data `enrollments` |
| 좌석 정합성 | Redis 남은 좌석과 Data 신청 수의 합이 정원과 같음 | Envoy 경유 ListOfferings |

## 4. 변수와 수준

| 변수 | 수준 (넉넉함에서 최소 순) | 바꾸는 위치 |
|---|---|---|
| 서비스별 복제 수 | 2, 1 | sa-app2 의 auth, academic, enrollment 중지 |
| 컨테이너 CPU 한도 | 2.0, 1.0, 0.5 | compose `cpus` |
| 컨테이너 메모리 한도 | 1g, 512m, 256m | compose `mem_limit` 와 JVM 힙 |
| QUEUE_MAX_ACTIVE | 200, 100, 50 | enrollment 와 queue-worker 의 `.env` |
| VM 수 | 5, 4, 3, 1 | 서비스 배치 변경, 1대는 `deploy/allinone` |

## 5. 실행 순서

한 번에 한 변수만 줄이고, 앞 단계에서 찾은 최소값은 다음 단계에서 그대로 유지합니다.
구성 이름은 `R복제_C CPU_M메모리_Q한도_V대수` 규칙을 따릅니다.

| 단계 | 구성 이름 | 복제 | CPU | 메모리 | QUEUE_MAX_ACTIVE | VM |
|---|---|---|---|---|---|---|
| 0 | R2_C2.0_M1g_Q200_V5 | 2 | 2.0 | 1g | 200 | 5 |
| 1 | R1_C2.0_M1g_Q200_V5 | 1 | 2.0 | 1g | 200 | 5 |
| 2 | R?_C1.0_M1g_Q200_V5 | 1단계 결과 | 1.0 | 1g | 200 | 5 |
| 2 | R?_C0.5_M1g_Q200_V5 | 1단계 결과 | 0.5 | 1g | 200 | 5 |
| 3 | R?_C?_M512m_Q200_V5 | 앞 결과 | 앞 결과 | 512m | 200 | 5 |
| 3 | R?_C?_M256m_Q200_V5 | 앞 결과 | 앞 결과 | 256m | 200 | 5 |
| 4 | R?_C?_M?_Q100_V5 | 앞 결과 | 앞 결과 | 앞 결과 | 100 | 5 |
| 4 | R?_C?_M?_Q50_V5 | 앞 결과 | 앞 결과 | 앞 결과 | 50 | 5 |
| 5 | R?_C?_M?_Q?_V4, V3, V1 | 앞 결과 | 앞 결과 | 앞 결과 | 앞 결과 | 4, 3, 1 |

0단계가 통과하지 못하면 자원을 줄이는 실험을 시작하지 않고 병목을 먼저 찾습니다.
QUEUE_MAX_ACTIVE 는 자원이 아니라 동시 입장 인원이므로, 낮출수록 서버 부하는 줄지만 마지막 학생의 입장 대기 시간은 늘어납니다. 이 값은 `time_to_admit` 과 함께 보고합니다.

## 6. 중단 규칙

어떤 수준에서 통과 기준이 하나라도 깨지면 같은 구성을 한 번 더 실행합니다.
두 번 모두 깨지면 그 변수의 최소값은 직전 수준으로 확정하고, 그 값을 고정한 채 다음 단계로 넘어갑니다.
마지막 단계까지 통과한 가장 작은 구성이 최소 자원 구성입니다.

## 7. 실행 방법

각 실행 전에는 부하 학생의 신청과 대기열이 비어 있어야 합니다. `run.sh` 는 시작 전에 Data 를 확인하여 부하 학생의 ENROLLED 행이 남아 있으면 멈춥니다. 초기화와 자원 변경은 Orca VMs 탭의 각 VM 창에서 수행합니다.

```bash
TARGET=192.168.64.30:8080 DATA_ADDR=192.168.64.33:9200 \
CFG_REPLICAS=2 CFG_CPU=2.0 CFG_MEM=1g CFG_QUEUE_MAX_ACTIVE=200 CFG_VMS=5 \
experiments/run.sh R2_C2.0_M1g_Q200_V5
```

결과는 `experiments/results/<구성 이름>_<시각>/` 에 남습니다. `config.env` 에 구성과 판정이, `summary.json` 에 k6 전체 요약이, `verify-post.txt` 에 정원과 정합성 확인 결과가 들어 있습니다. 모든 실행의 한 줄 요약은 `experiments/results/index.tsv` 에 쌓입니다.
컨테이너별 CPU 와 메모리 사용량은 Grafana 화면이나 VMs 탭의 `docker stats` 로 같은 시각에 따로 기록합니다.
