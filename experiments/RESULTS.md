# 최소 자원 탐색 실험 결과

## 1. 요약

학생 3,660명이 오픈 전에 미리 로그인해 두고 오픈 시각부터 2초 안에 한꺼번에 대기열에 들어오는 조건에서, 통과 기준을 지킨 가장 작은 구성은 `R1_C0.5_M512m_Q200_V3` 입니다. 앱 서비스(auth, academic, enrollment)를 하나씩만 sa-infra 에 올리고 컨테이너마다 CPU 0.5, 메모리 512m, 힙 256m 를 주었으며 동시 입장 한도는 200명입니다. 이 구성은 VM 을 sa-lb, sa-db, sa-infra 세 대만 쓰며, 두 번 실행하여 두 번 모두 오류 0건과 수강신청 p95 782ms, 305ms 를 기록했습니다.

## 2. 실험 조건

2026년 10월 24일 17시 59분부터 20시 8분까지 다섯 VM 에서 18회 실행했습니다. 부하 학생은 30000001 ~ 30003660 의 3,660명이고 신청 대상은 개설 강의 101 ~ 110 의 3,000석이며, 부하는 Mac 의 k6 v2.3.0 이 sa-lb Envoy `192.168.64.30:8080` 으로 직접 보냈습니다. 매 실행 뒤에는 sa-infra 창에서 `experiments/reset-load.sh` 로 부하 학생의 신청과 대기열, 좌석만 되돌렸고, Mac 의 부하 평균을 실행 시작과 끝에 `config.env` 의 `HOST_LOAD_START`, `HOST_LOAD_END` 로 남겼습니다. 이번 실험 동안 Mac 의 1분 부하 평균은 1.9 ~ 11.0 이었습니다.

한 번의 실행은 두 단계로 나뉩니다. 첫 단계에서는 3,660명이 오픈 120초 전부터 90초 동안 고르게 나뉘어 로그인하며, 시간 초과 같은 일시 오류는 여섯 번까지 다시 시도합니다. 둘째 단계에서는 오픈 시각부터 2초 안에 모든 학생이 대기열에 들어가 입장을 기다린 뒤 강의 목록 조회, 1 ~ 2과목 신청, 내 신청 목록 조회, 입장권 반납을 차례로 수행합니다. 로그인 토큰은 2시간 동안 유효하고 한 번의 실행은 4분 안팎이므로 둘째 단계에서 토큰이 만료되지 않습니다.

통과 기준은 둘째 단계에만 적용합니다. 오픈 후 RPC 오류율과 수강신청 오류율이 모두 4.00% 미만이고 수강신청 p95 가 2,000ms 이하여야 하며, 둘째 단계에서 실패한 학생과 정원 초과가 없고 Data 의 부하 학생 ENROLLED 행 수가 k6 성공 건수와 같아야 합니다. 첫 단계의 로그인 오류와 지연은 따로 기록하고 판정에는 넣지 않았습니다. 정원 마감과 같은 과목 중복 같은 업무상 거절은 오류로 세지 않습니다.

## 3. 측정 도구와 설정 변경

이번 실험을 위해 `experiments/k6/enroll-open.js` 와 `experiments/run.sh` 를 다음과 같이 고쳤고 Java 코드는 바꾸지 않았습니다.

1. 로그인을 오픈 전 단계로 옮기고 로그인 오류를 `login_error_rate`, `login_errors`, `login_failed` 로 따로 세도록 했습니다. 오픈 후 RPC 오류율에는 로그인이 들어가지 않습니다.
2. 첫 실행에서 대기 시간이 30초를 넘은 학생의 입장 대기 스트림이 k6 의 일반 요청 제한 시간(30초)에 걸려 989건의 오류로 잡혔습니다. 콘솔 클라이언트는 이 스트림에 제한 시간을 두지 않으므로, k6 도 입장 대기 제한(1,800초)까지 스트림을 열어 두도록 바꾸었습니다.
3. 실패 학생을 단계별로, RPC 오류를 호출별로 나누어 `summary.json` 에 남기도록 했습니다.
4. `run.sh` 는 실패 학생이 있으면 FAIL 로 판정하고, 결과 표에 사전 로그인 실패 수와 오류율, 지연을 함께 적습니다.

앞선 1차 실험에서 고친 것도 그대로 적용되어 있습니다. k6 gRPC 상태 값을 숫자로 비교하도록 고쳐 재시도와 업무상 거절 판정이 제대로 동작하고, `reset-load.sh` 가 열 분반의 좌석을 모두 되돌리며, Envoy 는 auth 로 가는 동시 요청을 앱 VM 당 16개로 제한하고 로그인 제한 시간을 30초로 둡니다. sa-lb 의 Envoy 메모리 한도는 512m 입니다.

## 6. 병목

로그인을 오픈 전으로 옮기자 auth 는 오픈 구간에 CPU 를 거의 쓰지 않았고(0 ~ 10%), 부하는 enrollment 한 곳에 모였습니다. enrollment 는 오픈 직후 2초 동안 3,660건의 대기열 진입을 받고, 입장을 기다리는 학생마다 대기 스트림을 하나씩 열어 둔 채 1초마다 순번을 보냅니다. 그래서 enrollment 의 자원 한계는 다음 세 가지 형태로 나타났습니다.

1. **CPU.** CPU 0.5 에서 enrollment 는 오픈 구간 내내 한도(51 ~ 54%)에 붙어 있었고 수강신청 p99 가 1.3 ~ 3.7초로 늘었습니다. 0.25 에서는 사전 로그인조차 처리하지 못했습니다(로그인 p95 30초, 오류율 88.36%).
2. **메모리.** 복제가 하나이면 열린 대기 스트림 3,660개가 한 enrollment 에 몰리므로, 컨테이너 메모리 최고값이 190 ~ 388MiB 까지 올라갔습니다. 384m 와 256m 에서는 컨테이너가 메모리 한도에 걸려 강제 종료되었고(10번과 13번, 커널 로그의 `Memory cgroup out of memory`), 강제 종료가 없었던 11, 12번에서도 응답이 5초를 넘긴 요청이 생겼습니다.
3. **동시 입장 한도와 CPU 의 상호작용.** QUEUE_MAX_ACTIVE 를 100 으로 낮추면 기다리는 학생이 늘어 대기 스트림 갱신이 많아지고, CPU 0.5 에서는 대기열 진입 처리 시간이 최대 5.6초까지 늘어 Envoy 의 5초 제한에 걸렸습니다. 16번에서 서버는 대기열 진입 3,662건을 모두 처리했지만 그 가운데 673건이 5초를 넘겨, 학생 663명이 대기열 진입 단계에서 실패했습니다. 따라서 CPU 를 0.5 로 줄인 구성에서는 동시 입장 한도를 낮추어도 부하가 줄지 않고 오히려 실패가 늘었습니다.

VM 3대 구성이 4대 구성보다 수강신청 꼬리 지연이 짧았던 것(p99 1.3 ~ 1.4초와 1.7 ~ 2.8초)은 enrollment 와 Redis, Kafka 가 같은 VM 에 있어 VM 사이 왕복이 줄었기 때문으로 보입니다. 다만 각 구성은 두 번씩만 실행했고 Mac 부하도 실행마다 달랐으므로 이 차이는 경향으로만 봅니다.

## 7. 1차 실험과의 비교

같은 날 17시 9분부터 17시 49분까지 오픈 시각에 로그인까지 함께 몰리는 조건으로 15회를 먼저 실행했으며, 그 기록은 `experiments/results/index.tsv` 와 같은 폴더의 실행별 디렉터리에 있습니다. 그때는 3,660건의 로그인이 2초 안에 몰리면서 비밀번호 해시 계산(PBKDF2 100,000회)이 auth 의 CPU 를 다 썼고, 로그인 p95 가 26 ~ 28초로 k6 의 30초 제한 바로 아래에 있었습니다. 그 결과 기준 구성조차 여섯 번 가운데 세 번만 통과했고, 복제 1과 CPU 1.0 은 로그인 시간 초과로 RPC 오류율 4.81 ~ 9.49% 를 기록했습니다. 로그인을 오픈 전으로 옮긴 2차 실험에서는 같은 기준 구성이 오류 0건으로 통과했고, 최소 구성도 앱 CPU 합계 12.0 에서 1.5 로, VM 5대에서 3대로 줄었습니다.

| 구분 | 1차 실험 (로그인 포함) | 2차 실험 (사전 로그인) |
|---|---|---|
| 기준 구성 통과 | 6회 중 3회 | 2회 중 2회 |
| 기준 구성 RPC 오류율 | 0.00 ~ 17.85% | 0.00% |
| 복제 1 | 실패 (4.81%, 4.84%) | 통과 (0.00%) |
| CPU 1.0 | 실패 (9.49%, 6.96%) | 통과 (0.00%) |
| 판정을 가른 요인 | 로그인 계산량과 auth CPU | enrollment 의 CPU 와 메모리 |
| 최소 구성 | 기준 구성 (불안정) | R1_C0.5_M512m_Q200_V3 |

## 8. 확인하지 못한 것

1. 각 수준은 중단 규칙에 따라 한두 번만 실행했으므로 최소 구성이 매번 통과한다고 보장할 수는 없습니다. 특히 CPU 0.5 와 메모리 512m 는 여유가 적어, 16번에서 enrollment 메모리가 512m 가운데 388MiB 까지 올라갔습니다.
2. QUEUE_MAX_ACTIVE 100 이 CPU 1.0 이상에서 통과하는지는 시험하지 않았습니다. 19시 39분에 run.sh 를 거치지 않고 같은 구성(R1_C0.5_M512m_Q100_V4)으로 진단 실행을 한 번 했을 때는 오류 0건으로 통과했으므로, 이 구성은 통과와 실패의 경계에 있습니다.
3. QUEUE_MAX_ACTIVE 50, VM 2대와 1대 구성은 실행하지 않았습니다.
4. k6 가 학생 한 명의 입장을 놓치는 원인(4번)은 찾지 못했습니다.
5. 다섯 VM 과 k6 가 모두 같은 Mac 에서 돌기 때문에 실제 서버에서의 처리량과는 다를 수 있습니다.

## 9. 최종 상태

실험을 마친 뒤 VM 은 최소 구성으로 두었고, 마지막 실행 뒤 `reset-load.sh` 로 부하 학생의 신청 3,000건을 지우고 분반 101 ~ 110 을 300석으로 되돌렸습니다.

| VM | 상태 |
|---|---|
| sa-lb | Envoy 실행, `deploy/lb/.env` 에 `ENVOY_MEM=512m`. VM 의 `deploy/lb/envoy.yaml` 은 앱 엔드포인트 `192.168.64.31` 을 `192.168.64.34` 로 바꾼 것이고, 저장소 파일은 실험 뒤 `192.168.64.34` 하나만 가리키도록 맞추었습니다. |
| sa-app1 | 앱 서비스 세 개 중지, `.env` 는 CPU 0.5, 512m, 256m, QUEUE_MAX_ACTIVE 200 |
| sa-app2 | 앱 서비스 세 개 중지, `.env` 는 CPU 2, 512m, 256m, QUEUE_MAX_ACTIVE 200 |
| sa-db | Data 실행, 기본값 |
| sa-infra | 인프라 컨테이너와 함께 `deploy/app` 의 auth, academic, enrollment 실행. `deploy/app/.env` 는 CPU 0.5, 512m, 256m, QUEUE_MAX_ACTIVE 200, `SERVER_NAME=sa-infra` 이고 JWT 비밀 값은 sa-infra 에서 새로 만들었습니다. `deploy/infra/.env` 는 QUEUE_MAX_ACTIVE 200 입니다. |

저장소의 compose 기본값과 `deploy/lb/envoy.yaml` 은 이 최소 구성입니다. 5대 구성으로 되돌리는 방법은 `deploy/README.md` 의 "5대 구성"에 있습니다. sa-infra 의 JWT 비밀 값은 앱 VM 과 다르므로 앱 VM 과 sa-infra 의 앱 서비스를 함께 켜면 안 됩니다.

2차 실험의 한 줄 요약은 `experiments/results/prelogin/index.tsv` 에, 실행별 기록은 `experiments/results/prelogin/<구성 이름>_<시각>/` 에 있습니다.
