# 최소 자원 탐색 실험 결과

## 1. 실험 조건

2026년 10월 24일 17시 9분부터 17시 49분까지 sa-lb, sa-app1, sa-app2, sa-db, sa-infra 다섯 VM에서 `experiments/MATRIX.md` 의 고정 부하를 15회 걸었습니다. 학생 30000001 ~ 30003660 의 3,660명이 오픈 시각부터 2초 안에 도착하며, 부하는 Mac 의 k6 v2.3.0 이 Envoy `192.168.64.30:8080` 으로 직접 보냈습니다. 매 실행 뒤에는 sa-infra 창에서 `experiments/reset-load.sh` 로 부하 학생의 신청과 대기열, 좌석만 되돌렸습니다.

VM 크기가 MATRIX 의 구성보다 작으므로 수준을 VM 에 맞게 조정했습니다. 앱 VM 한 대(2 vCPU, 1,955MiB)에 auth, academic, enrollment 세 컨테이너가 함께 있어 컨테이너당 1g 는 들어가지 않으므로, 기준 구성은 컨테이너당 메모리 512m 와 힙 256m 로 정하고 줄이는 수준을 384m(힙 192m)와 256m(힙 128m)로 두었습니다. CPU 와 메모리 한도는 앱 계층 세 서비스에 똑같이 적용했고 Data(1 CPU, 640m), queue-worker 와 enrollment-consumer(1 CPU, 384m), Kafka(1 CPU, 1g), Redis(1 CPU, 256m)는 기본값으로 고정했습니다. 구성 이름은 `R복제_C CPU_M메모리_Q한도_V대수` 규칙을 따릅니다.

통과 기준은 수강신청 오류율과 전체 RPC 오류율이 모두 4.00% 미만이고 수강신청 p95 가 2,000ms 이하이며, 실패 학생과 정원 초과가 0이고 Data 저장 건수와 Redis 좌석이 k6 성공 건수와 맞는 것입니다.

## 2. 실험 중 바로잡은 것

첫 실행에서 측정 도구와 설정의 문제 세 가지가 드러나 고친 뒤 실험을 이어 갔습니다.

1. k6 의 gRPC 상태 값은 문자열이 아니라 객체여서 `Set.has` 로 비교하면 항상 거짓이 됩니다. 그 결과 재시도할 오류(UNAVAILABLE, DEADLINE_EXCEEDED, RESOURCE_EXHAUSTED)를 한 번도 재시도하지 않았고, 업무상 거절(ALREADY_EXISTS, ABORTED 등)도 오류로 세고 있었습니다. 상태 값을 숫자로 바꾸어 비교하도록 `experiments/k6/enroll-open.js` 를 고쳤습니다.
2. `reset-load.sh` 의 좌석 복원 반복문 안에서 `docker compose exec` 가 표준 입력을 읽어 첫 분반(101)만 300석으로 되돌리고 나머지는 그대로 두었습니다. exec 의 입력을 `/dev/null` 로 막아 열 분반이 모두 300석으로 돌아오는 것을 확인했습니다.
3. `run.sh` 는 실패 학생 수를 판정에 넣지 않아 269명이 실패한 실행(4번)도 PASS 로 적었습니다. 실패 학생이 1명이라도 있으면 FAIL 로 판정하도록 고쳤고 4번의 기록도 FAIL 로 바로잡았습니다.

설정은 두 가지를 바꾸었습니다. 1, 2번 실행에서 로그인이 한꺼번에 auth 로 들어가 3,660건이 동시에 비밀번호 해시(PBKDF2 100,000회)를 계산하자, 모든 요청이 함께 느려져 Envoy 의 5초 제한에 걸렸고 로그인 성공은 502명과 804명에 그쳤습니다. 같은 auth 에 동시 요청을 8개와 32개로 제한해 보면 초당 245건과 279건을 처리했으므로, 처리 능력보다 동시에 받아들이는 양이 문제였습니다. 그래서 `deploy/lb/envoy.yaml` 의 auth 클러스터에 앱 VM 하나당 연결 1개와 연결당 동시 스트림 16개의 한도를 두고 auth 경로의 제한 시간을 30초로 늘려, 넘치는 로그인이 Envoy 에서 순서대로 기다리도록 했습니다. 이 변경 뒤 로그인만 3,660건을 2초 안에 보내는 시험에서 3,660건이 모두 성공했고 최대 9.45초가 걸렸습니다. 또한 3번 실행에서 Envoy 메모리가 256MiB 한도 가운데 240MiB 까지 올라가서 sa-lb 의 `.env` 에 `ENVOY_MEM=512m` 을 적었습니다.

## 4. 최소 자원 구성

통과한 구성은 기준 구성 `R2_C2.0_M512m_Q200_V5` 하나뿐이며, 이 구성도 여섯 번 가운데 세 번(3, 5, 6번)만 통과했습니다. 따라서 이 실험 환경에서 정할 수 있는 최소 구성은 다음과 같습니다.

| 항목 | 값 |
|---|---|
| 앱 VM | 2대, 각 VM 에 auth, academic, enrollment 하나씩 |
| 앱 컨테이너 | CPU 2.0, 메모리 512m, 힙 256m |
| QUEUE_MAX_ACTIVE | 200 |
| VM | 5대 |
| Envoy | auth 로 가는 동시 스트림을 앱 VM 당 16개로 제한, 로그인 제한 시간 30초, 메모리 512m |

복제 수를 1로 줄인 7, 8번과 CPU 를 1.0 으로 줄인 9, 10번은 두 번 모두 로그인 시간 초과로 실패했으므로 중단 규칙에 따라 복제 2와 CPU 2.0 이 최소값입니다. 메모리 384m 와 256m(11, 12, 13번)도 실패했지만, 같은 시간대에 기준 구성으로 돌린 대조 실행(14, 15번)도 실패했으므로 메모리 때문에 실패했다고 볼 수 없습니다. 실제로 앱 컨테이너의 메모리 최고값은 모든 실행에서 166MiB 이하였고 256m 한도에서도 메모리 부족 종료는 없었으므로, 메모리 수준은 판정하지 못한 것으로 둡니다. QUEUE_MAX_ACTIVE 100 과 50, VM 3대와 1대 단계는 기준 구성부터 안정적으로 통과하지 못해 실행하지 않았습니다.

## 5. 병목

병목은 수강신청이 아니라 오픈 시각에 몰리는 로그인입니다. 대기열과 Redis 좌석 차감, Kafka 를 거친 Data 반영으로 이어지는 수강신청 경로는 복제 1, CPU 1.0, 메모리 256m 에서도 수강신청 오류율 0.00% 와 p95 297ms 이하를 지켰습니다. 반면 로그인은 한 건마다 PBKDF2 100,000회를 계산하므로 3,660명이 2초 안에 몰리면 auth 의 CPU 가 처리량을 정합니다. 기준 구성에서 로그인 p95 는 26.7 ~ 27.9초로 k6 의 30초 제한 바로 아래에 있어, 처리량이 조금만 떨어져도 마지막 학생들의 로그인이 30초를 넘깁니다. 복제를 하나로 줄이거나 CPU 를 1.0 으로 낮추면 auth 가 쓸 수 있는 CPU 가 절반이 되어 RPC 오류율이 4.81 ~ 9.49% 로 올라갔습니다.

이 판정은 실험 환경의 영향을 크게 받습니다. 다섯 VM 은 모두 Mac 한 대(10코어) 위의 UTM 가상 머신이고 k6 의 3,660 VU 도 같은 Mac 에서 돌기 때문에, 다른 작업이 Mac 의 CPU 를 쓰면 VM 의 처리량이 함께 떨어집니다. 동시 요청 8개로 잰 로그인 처리량은 17시 13분에 초당 245건(중앙값 29ms)이었으나 17시 46분과 17시 50분에는 초당 140건과 143건(중앙값 53ms, 48ms)으로 떨어졌고, 이때 Mac 의 1분 부하 평균은 8 ~ 17이었으며 문서 변환 같은 다른 작업이 CPU 를 쓰고 있었습니다. VM 안에서는 steal 시간이 보이지 않으므로 이 차이는 VM 바깥에서 생긴 것으로 판단합니다. 15번부터는 시작과 끝의 Mac 부하 평균을 `config.env` 에 남겼습니다.

## 6. 남은 과제

다음은 이 실험에서 확인하지 못했거나 코드 변경이 필요해 하지 않은 것입니다.

1. 로그인 비용을 줄이는 변경은 Java 코드를 고쳐야 하므로 하지 않았습니다. 해시 반복 횟수를 낮추거나, 실제 수강신청처럼 학생이 오픈 전에 미리 로그인하고 오픈 시각에는 대기열 진입부터 시작하도록 시나리오를 바꾸면 로그인 병목이 사라질 것으로 예상하지만 측정하지 않았습니다.
2. Mac 의 다른 부하를 멈춘 상태에서 기준 구성과 메모리 256m 를 번갈아 다시 돌려야 메모리 최소값을 판정할 수 있습니다.
3. 로그인 3,660명 가운데 입장 3,659명에 실패 0명으로 집계된 실행(5, 7, 12번)이 있어 k6 집계에서 학생 한 명이 빠지지만 그 원인은 찾지 못했습니다. 이 실행들에서도 Data 와 Redis 의 건수는 모두 맞았습니다.
4. QUEUE_MAX_ACTIVE 100 과 50, VM 통합 단계는 실행하지 않았습니다.

## 7. 최종 상태

실험을 마친 뒤 VM 은 기준 구성으로 두었습니다. sa-app1 과 sa-app2 의 `deploy/app/.env` 에는 `APP_CPUS=2`, `APP_MEM=512m`, `APP_HEAP=256m`, `QUEUE_MAX_ACTIVE=200` 이, sa-infra 의 `deploy/infra/.env` 에는 `QUEUE_MAX_ACTIVE=200` 이, sa-lb 의 `deploy/lb/.env` 에는 `ENVOY_MEM=512m` 이 들어 있고, Envoy 는 바뀐 `envoy.yaml` 로 동작합니다. 마지막 실행 뒤 `reset-load.sh` 로 부하 학생의 신청 3,000건을 지우고 분반 101 ~ 110 을 300석으로 되돌렸습니다.

전체 한 줄 요약은 `experiments/results/index.tsv` 에, 실행별 기록은 `experiments/results/<구성 이름>_<시각>/` 에 있습니다.
